## Findings

1. **Unnumbered sections lose `numbered="false"`** — (a) section.rb:151-163 `clause_parse`, `numbered: node["numbered"]`. (b) Old passed the clause's `@numbered` attribute through to the RFC `<section>`. New leg: metanorma-document 0.2.9 Clause maps only `@unnumbered` (as `:boolean`), never `@numbered` which is what metanorma-ietf's standoc converter emits (converter.rb:121 `attrs[:numbered]`); and even for an `unnumbered="true"` input, section_transformer.rb:213-216 compares the boolean against the string `"true"`, which is always false. (c) AsciiDoc `[numbered=false]` on a clause (the documented IETF idiom) → semantic `<clause numbered="false">` → RFC XML section emitted with no `numbered` attribute → xml2rfc numbers it. Confirmed end-to-end with a probe document. (d) **High**.

2. **`removeInRFC` sections lose the attribute** — (a) section.rb:151-163, `removeInRFC: node["removeInRFC"]` (also annexes via section.rb:172). (b) Old passed `@removeInRFC` through to `<section removeInRFC="true">`, which tells xml2rfc to strip the section when the draft becomes an RFC. (c) AsciiDoc `[removeInRFC=true]` clause → attribute absent from output (confirmed end-to-end); the section will wrongly survive into the published RFC. No mapping exists in the 0.2.9 model (parse ghost) and no side-channel recovery à la `recover_rfc_attributes` exists for it. (d) **High**.

3. **Annotations (`<cref>`) are never emitted** — (a) section.rb:178-182 `comments` → blocks.rb:187 `review_note_parse`, emitting `<cref anchor display source from>` with parsed children, gated on `render-document-annotations == "true"` or `//bibdata/ext/notedraftinprogress`. (b) Old rendered document reviews/annotations as RFC `cref` comments in back matter. New leg: annotation_transformer.rb:19 `build_annotations` returns `[]` unconditionally; the ported gate `render_annotations?` (annotation_transformer.rb:8) is dead code that nothing calls. (c) An AsciiDoc reviewer note (`[reviewer=X]`) in a document with `:notedraftinprogress:` set → no `<cref>` anywhere in the output (confirmed end-to-end; ANNOTBODY absent). (d) **High** (the stub shape suggests "not yet implemented" rather than by-design).

4. **Inline markup inside section titles is destroyed, content included** — (a) section.rb:144-149 `clause_parse_title`: title children are parsed recursively into `<name>`, preserving em/strong/xref/etc. (v3 `<name>` legally contains inline elements). (b) New leg builds `name.content = [ls_text(title)]` (section_transformer.rb:225-231); base.rb `ls_text` returns only the model's string runs, so a title's child-element content is not merely flattened — it disappears. (c) `== Plain _emphasized_ tail` → old: `<name>Plain <em>emphasized</em> tail</name>`; new: `<name>Plain  tail</name>` (empirically confirmed — the word "emphasized" is gone from the document). Same mechanism affects terms-section titles (term_transformer.rb:12-18) and term designations. (d) **High**.

5. **Generic preface clauses and executive summary dropped from middle** — (a) section.rb:164-170 `clause`: xpath walks `//preface/child::*[not(abstract|foreword)]`, i.e. introduction, acknowledgements, executivesummary, **and any plain preface `<clause>`** into `<middle>`. (b) New build_middle (section_transformer.rb:11-22) handles only `preface.introduction` and `preface.acknowledgements`; the Preface model's `content` (mapped from `clause`) and `executivesummary` attributes are never read. (c) An AsciiDoc `[.preface]`-classed clause, or an `[abstract]`-less document with an executive summary → its body text vanishes from the RFC (confirmed end-to-end: PREFCLAUSEBODY and EXECSUMBODY both absent). (d) **High** for preface clauses; **medium** for executivesummary (rare in IETF authoring, but the old leg rendered it).

6. **Multi-paragraph single definition now renders as a fake ordered list** — (a) terms.rb:64-84 `termdef_parse`/`multidef`: the `<ol><li>` wrap fires only when a term has **more than one `<definition>` element**; a single definition with several paragraphs rendered as sequential `<t>`s. (b) New leg (term_transformer.rb:123-150) counts definition *paragraphs*, so one definition with two `<p>`s becomes `<ol><li><t>…</t></li><li><t>…</t></li></ol>`, misrepresenting one definition as two enumerated ones. (c) A term whose single verbal-definition contains two paragraphs (empirically confirmed: DEFPARA1/DEFPARA2 wrapped in ol). (d) **Medium** — content survives but structure and enumeration semantics are wrong.

7. **`tocDepth`, `indexInclude`, `iprExtract` root attributes not emitted** — (a) section.rb:55-88 `rfc_attributes` reads `//bibdata/ext/{tocDepth,indexInclude,iprExtract}` onto the `<rfc>` root. (b) New `recover_rfc_attributes` (transformer.rb:128-136) recovers only symRefs/tocInclude/sortRefs; `set_rfc_attributes`/`set_rfc_attribute_channel` (metadata_transformer.rb:19-52) never set toc_depth/index_include/ipr_extract. Since xml2rfc v3 ignores the `<?rfc tocdepth?>` PI (as this branch's own F5 comment states), the author's `:toc-depth:` setting is silently overridden by the xml2rfc default. (c) AsciiDoc `:toc-depth: 2` → no `tocDepth` root attribute → xml2rfc renders 3-level TOC. (d) **High** for tocDepth (exactly parallels the fixed F5 trio); **medium** for indexInclude/iprExtract (rarer).

8. **Legacy PI coverage cut from ~35 keys to 8** — (a) section.rb:4-43 `common_rfc_pis`. (b) New PI_ORDER (metadata_transformer.rb:54) emits sortrefs/symrefs/tocdepth/subcompact/compact/strict/notedraftinprogress/comments only; `//pi/artworkdelimiter`, `inline`, `private`, `header`, `footer`, `text-list-symbols`, `tocinclude` etc. are dropped. (c) A document setting `:inline:` or `:private:` PIs → PI absent from output. (d) **Low** — xml2rfc v3 ignores nearly all legacy PIs, so observable impact is limited to v2-tooling consumers; still a deliberate-looking narrowing worth recording.

9. **Term-source cross-reference emitted as escaped literal markup** — (a) terms.rb:130-150 `preprocess_termref`/`termref_parse`: the origin `<origin>`/eref is *parsed* into a real `<xref>`/`<eref>` element inside `<t>[SOURCE: …]</t>`, carrying citeas text and locality (section number). (b) New `transform_term_source` (term_transformer.rb:265-306) concatenates `"<xref target='X'/>"` into a Text content string; the serializer escapes it, so the final RFC XML reads `<t>[SOURCE: &lt;xref target='RFC2119'/&gt;, adapted]</t>` — readers see raw angle-bracket markup and there is no live cross-reference; the locality ("section 5") and citeas display are also gone (the code comment concedes the locality model gap). (c) Any `[SOURCE]` term source with a bibliographic origin (empirically confirmed). Same string-splice pattern at block_transformer.rb:637 (`[term defined in <xref…>]`) is suspect for the identical escaping. (d) **High**.
   NOTE (Garak): the WS5-era mechanism for SOURCE xrefs relied on raw-serialization; verify against the F-series treatment before accepting — but agent claims empirical confirmation of ESCAPED output.

10. **Term-source modification text lost unless status="modified"** — (a) terms.rb:130-137 `preprocess_termref` calls `termsource_add_modification_text` unconditionally: modification text is appended (— …) whatever the status, including "adapted" or none. (b) New leg appends modification only inside the `when "modified"` branch (term_transformer.rb:288-295). (c) `<source status="adapted"><origin…/><modification><p>with changes</p></modification></source>` → old: `[SOURCE: RFC 2119, adapted — with changes]`; new: `[SOURCE: …, adapted]` (empirically confirmed: MODTEXT absent). (d) **High**.

11. **Multiple term sources no longer merged** — (a) terms.rb:134-136: consecutive `<source>` siblings merge into one bracket joined by "; " (`[SOURCE: A; B]`). (b) New emits one `<t>[SOURCE: …]</t>` per source (term_transformer.rb:206-210; empirically confirmed two separate `<t>`s). (c) A term citing two sources. (d) **Medium** — content survives; presentation diverges from the released output and from ISO house style.

12. **Requirement / recommendation / permission blocks vanish entirely** — (a) reqt.rb:4-27 plus the old preprocessing chain (`rfc_convert.rb` `document_preprocess` runs `@isodoc.permission/requirement/recommendation/requirement_render`): a reqt block rendered as `<t keepWithNext="true">` label followed by its fmt-provision content. (b) New leg: the shared presentation stage still produces `requirement` + `fmt-provision`, and the 0.2.9 model maps `clause.requirement/recommendation/permission` (clause_section.rb:63-69), but section_transformer.rb has no case for any of the three — SRC_TO_RFC_TAG (line 248) and both child walks skip them, so the whole block is silently dropped. (c) An AsciiDoc `[requirement]`/`[recommendation]`/`[permission]` block inside any clause → no trace in the RFC XML (empirically confirmed: REQBODY absent from output). (d) **High**.
